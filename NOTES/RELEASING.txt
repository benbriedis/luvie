Releasing Luvie
===============

Releases are built by GitHub Actions and triggered by pushing a version tag.
Everything else -- building on three platforms, testing, packaging, signing,
drafting the release -- is automatic.


Cutting a release
-----------------

1. Make sure main is green. Note the CI workflow does NOT run on every push --
   that trigger is commented out in .github/workflows/ci.yml -- so unless the
   commits arrived by pull request, run it by hand from the Actions tab first.

2. Tag and push:

       git tag -a v0.1.0 -m "Luvie 0.1.0"
       git push origin v0.1.0

   The tag must start with "v" -- that is what triggers .github/workflows/
   release.yml. It also becomes the version: both cmake/ProjectVersion.cmake
   (package file names) and cmake/GitVersion.cmake (the string `luvie --version`
   prints) run `git describe --tags`.

3. Wait for the workflow. It builds and smoke-tests on Ubuntu 22.04, macOS 14
   and Windows, packages each, installs the Linux packages on the
   distributions they target (see "Install tests" below), and creates a DRAFT
   release with everything attached.

4. Review the draft on GitHub, then publish it. Nothing is downloadable until
   you do -- that click is the only manual gate.


Install tests
-------------

Building and running Luvie on the build host proves the code works. It does not
prove the *package* works, and the two fail differently: a dependency the build
host happened to have installed and the package never declared, a file in a
prefix the target distribution does not use, an LV2 bundle no host can find.
None of that shows up until someone installs the thing.

So after packaging, release.yml installs each Linux package the way a user
would -- through the package manager, in a container of the target distribution
-- and runs tools/test-installed.sh against the result:

  test-packages       .deb on Debian 12 and Ubuntu 24.04, .rpm on Fedora. The
                      two .deb targets are not redundant: bookworm is close to
                      the Ubuntu 22.04 build host, noble is past the
                      64-bit-time_t library renames, so it checks the
                      dependencies still resolve there.

  test-aur-package    Builds packaging/aur/PKGBUILD with makepkg in an Arch
                      container exactly as an AUR user would, lints it with
                      namcap, then installs and tests the result. This is the
                      only automated check that recipe gets -- previously it was
                      built by hand at release time and nowhere else.

The script checks that luvie is on PATH and reports the version the tag says it
should, that every file the package promises is installed, that no binary has an
unresolved shared library, that the standalone starts and exits cleanly under
xvfb, and that an LV2 host (jalv, against a dummy-driver JACK server) finds the
plugin on its default search path and runs it.

The draft release is gated on all of it: an artifact that does not install is
not a release. It also runs standalone -- install a package by hand, then:

    sudo tools/test-installed.sh

Note the AUR job builds from the git tag named in the PKGBUILD, which is bumped
by hand only after a release goes out. On a tag build the workflow overrides
pkgver with the tag being released, so it tests the code in hand; on a
workflow_dispatch dry run there is no tag and it re-tests the last release.


What gets published
-------------------

Each package carries the standalone application AND the LV2 plugin. They used to
be a package each; splitting them asked people to choose between two downloads
that are useful together and cost nothing to ship as one.

  luvie_<ver>_amd64.deb                   app + plugin, Debian/Ubuntu
  luvie-<ver>-1.x86_64.rpm                app + plugin, Fedora/openSUSE
  Luvie-<ver>-macos-universal.dmg         Luvie.app + luvie.lv2, x86_64 + arm64
  luvie-<ver>-windows-x86_64-setup.exe    app + plugin, per-user installer
  luvie-<ver>-windows-x86_64.zip          app + plugin

Arch is served by the AUR recipe (below). Any other Linux distribution builds
from source; BUILD covers it.

Windows gets two artifacts on purpose. Neither is signed, so both raise the same
SmartScreen warning -- but browsers block unsigned .exe downloads far more
readily than .zip ones, so the zip is the download that always works while the
installer is the one that puts the plugin where hosts look. A third route,
packaging/scoop/, raises no warning at all, because Scoop does not set
mark-of-the-web on what it downloads; it needs no per-release work, since the
manifest carries checkver/autoupdate. See packaging/scoop/README.

macOS went from a zip to a disk image at v0.0.5: the image can hold an
/Applications symlink to drag onto, shows its README.txt on opening, and is the
only one of the two that can carry a stapled notarization ticket if signing is
ever turned on. A .pkg was considered and rejected -- it needs a second Apple
certificate type ("Developer ID Installer") and an unsigned one cannot be opened
at all on current macOS.

Two Linux artifacts have been dropped along the way, both for the same reason --
they hand someone a directory of files and leave the installing to them.

An AppImage, until v0.0.2: with libstdc++ and libgcc already linked statically it
bundled only the Xft/Xcursor/Xinerama group on top of what a plain archive needs,
could not improve on the glibc floor (an AppImage cannot bundle glibc either),
and was the one artifact that could not carry the plugin at all, since a host
cannot scan inside a sealed AppImage.

A generic .tar.gz, until v0.0.4: it installed nothing, owned nothing, and could
not be upgraded or removed. Every question it raised -- where does luvie.lv2 go,
why is there no menu entry, why is the icon missing -- is one the .deb and .rpm
answer by construction, and building from source is no more work than unpacking
an archive into the right places by hand.

The Linux binaries' glibc floor is set by the runner they are built on (Ubuntu
22.04, glibc 2.35). Moving that job to a newer runner silently drops support for
older distributions.

The .deb declares Replaces/Conflicts on the old luvie-lv2 package, so upgrading
from v0.0.2 or earlier removes it rather than failing on the shared files. The
.rpm carries no equivalent -- luvie-lv2 was never published as one.

The .rpm is built on the same Ubuntu runner as the .deb, by CPack's RPM
generator (Debian's `rpm` package supplies rpmbuild). rpmbuild does not care
what distribution it runs on, and the dependencies it derives are soname-based,
so they resolve against the target system rather than the build host.

It is the one package that puts the plugin in /usr/lib64/lv2 rather than
/usr/lib/lv2: Fedora and openSUSE compile lilv with a search path that has no
/usr/lib/lv2 entry, so a bundle there is invisible to every host on the system.
Since all three Linux packages come out of one `cpack` over one build, the .rpm
gets there by moving the staged files -- cmake/RelocateLv2ForRpm.cmake, wired in
from cmake/Packaging.cmake. This was found by the Fedora install test below, and
the comment in cmake/Packaging.cmake used to assert the opposite.


Arch Linux (manual)
-------------------

Arch is served through the AUR, which produces no release artifact: an AUR
package is a PKGBUILD that each user's `makepkg` compiles from the release tag
on their own machine. So there is nothing to attach to the release -- but the
recipe itself is tested, by the test-aur-package job described above. Publishing
it is still manual.

The recipe lives at packaging/aur/PKGBUILD; packaging/aur/README has the
publishing procedure. In short, after publishing the GitHub release:

    cp packaging/aur/PKGBUILD ../aur-luvie/     # edit pkgver, reset pkgrel to 1
    cd ../aur-luvie
    extra-x86_64-build                          # build in a clean chroot
    namcap luvie-*.pkg.tar.zst
    makepkg --printsrcinfo > .SRCINFO
    git commit -am "Update to 0.0.5" && git push

Keep packaging/aur/PKGBUILD in step with anything that changes what Luvie links
or where it installs -- that copy is the master, and the AUR repository holds a
copy of it.


Dry run
-------

Run the Release workflow manually from the Actions tab (workflow_dispatch). It
builds and packages everything and uploads the artifacts, but the release job is
gated on a tag push, so nothing is published. Use this to check a packaging
change without spending a tag.


Code signing
------------

Luvie is published unsigned, deliberately: signing costs money on both platforms
and the only free option covers just one of them. What that costs users is
documented in the release notes body (see the end of release.yml) and in the
README.txt inside each archive.

  Windows   SmartScreen says "Windows protected your PC" -> More info -> Run
            anyway. Same for the installer and for the .exe in the zip, since
            signing is what removes it, not the choice of download. Installing
            through Scoop avoids it entirely (packaging/scoop/README).

  macOS     The app: first launch is refused, then System Settings -> Privacy &
            Security offers "Open Anyway". Note that right-click -> Open, which
            older instructions everywhere still recommend, was removed in macOS
            15 -- do not put it back.

            The plugin is the real cost. A quarantined, un-notarized bundle is
            not merely warned about, it is silently not loaded: the host lists
            nothing and reports nothing, so there is no symptom to search for.
            The fix is one command and it is spelled out at the top of the .dmg's
            README.txt, which is the main reason that file exists:

                xattr -dr com.apple.quarantine \
                    ~/Library/Audio/Plug-Ins/LV2/luvie.lv2

Where the money goes, checked August 2026:

  Apple     USD 99/year, recurring, for the Developer Program. It is the only
            source of a "Developer ID Application" certificate and there is no
            open-source exemption, no one-off purchase and no other vendor.
            Notarization is what removes both macOS problems above, including
            the plugin one.

  Windows   SignPath Foundation (signpath.org) gives free OV code signing to
            open-source projects, issued by Sectigo and driven from CI. Luvie
            qualifies: public repository, recognised licence, and the same person
            owning the repository and the signing. This is the one free option
            and applying is a one-off. Certum's open-source certificate (EUR
            25-90) is the fallback if that falls through, but certificates are
            capped at 459 days from February 2026, making it an annual renewal.

            Azure Trusted Signing (now "Artifact Signing", USD 9.99/month) looks
            attractive and is not available: individual onboarding is paused, and
            organisations must have three years of verifiable history in the US
            or Canada.

Turning signing on is a matter of adding secrets and changing no code -- the
workflow already implements both paths and skips them when unconfigured, which
is also what keeps forks building. Windows signing runs through
tools/sign-windows.ps1, called twice: over luvie.exe and the two plugin modules
before packaging, and over setup.exe afterwards. Signing the installer is where
it does the most good, being the file users actually execute.

Repository secrets (Settings -> Secrets and variables -> Actions):

  MACOS_CERT_P12        Developer ID Application cert + key, .p12, base64'd:
                            base64 -i cert.p12 | pbcopy
  MACOS_CERT_PASSWORD   the .p12 export password
  MACOS_SIGN_IDENTITY   e.g. "Developer ID Application: Your Name (TEAMID)"

  APPLE_ID              Apple ID for notarization (optional; enables stapling,
  APPLE_TEAM_ID         which removes the first-launch prompt completely --
  APPLE_APP_PASSWORD    an app-specific password, not the account password)

  WINDOWS_CERT_P12      code-signing cert + key, .pfx/.p12, base64'd
  WINDOWS_CERT_PASSWORD its export password

Signing is only as good as the certificate: macOS notarization specifically
requires a "Developer ID Application" certificate from a paid Apple Developer
account. A self-signed certificate will sign but will not satisfy Gatekeeper.

The two WINDOWS_ secrets suit a certificate you hold the key for. SignPath does
not work that way -- it holds the key and signs on request -- so going that route
means replacing the calls to tools/sign-windows.ps1 with SignPath's
submit-signing-request action, whose origin verification ties each signature to a
specific workflow run. That is a change to make once the application is approved,
not before.


If something fails
------------------

The tag stays put; fix the problem, delete the tag locally and remotely, and
re-push it:

    git tag -d v0.1.0
    git push --delete origin v0.1.0
    git tag -a v0.1.0 -m "Luvie 0.1.0"
    git push origin v0.1.0

Delete the draft release first if one was created, or the re-run will add a
second set of assets to it.

The dependency cache (keyed on CMakeLists.txt, which holds every pinned
revision) is the usual suspect for a build that fails only in CI. Clear it from
the Actions -> Caches page and re-run.
