Releasing Luvie
===============

Releases are built by GitHub Actions and triggered by pushing a version tag.
Everything else -- building on three platforms, testing, packaging, signing,
drafting the release -- is automatic.


Cutting a release
-----------------

1. Make sure main is green (the CI workflow runs on every push).

2. Tag and push:

       git tag -a v0.1.0 -m "Luvie 0.1.0"
       git push origin v0.1.0

   The tag must start with "v" -- that is what triggers .github/workflows/
   release.yml. It also becomes the version: both cmake/ProjectVersion.cmake
   (package file names) and cmake/GitVersion.cmake (the string `luvie --version`
   prints) run `git describe --tags`.

3. Wait for the workflow. It builds and smoke-tests on Ubuntu 22.04, macOS 14
   and Windows, packages each, and creates a DRAFT release with everything
   attached.

4. Review the draft on GitHub, then publish it. Nothing is downloadable until
   you do -- that click is the only manual gate.


What gets published
-------------------

Each package carries the standalone application AND the LV2 plugin. They used to
be a package each; splitting them asked people to choose between two downloads
that are useful together and cost nothing to ship as one.

  luvie_<ver>_amd64.deb                   app + plugin, Debian/Ubuntu
  luvie-<ver>-1.x86_64.rpm                app + plugin, Fedora/openSUSE
  luvie-<ver>-linux-x86_64.tar.gz         app + plugin, unpack anywhere
  Luvie-<ver>-macos-universal.zip         Luvie.app + luvie.lv2, x86_64 + arm64
  luvie-<ver>-windows-x86_64.zip          app + plugin

There was also a Linux AppImage until v0.0.2. It was dropped: with libstdc++
and libgcc already linked statically, it bundled only the Xft/Xcursor/Xinerama
group on top of what the tarball needs, shared the tarball's glibc floor exactly
(an AppImage cannot bundle glibc either), and was the one artifact that could not
carry the plugin, since a host cannot scan inside a sealed AppImage. The tarball
covers the same users for none of the machinery.

The Linux binaries' glibc floor is set by the runner they are built on (Ubuntu
22.04, glibc 2.35). Moving that job to a newer runner silently drops support for
older distributions.

The .deb declares Replaces/Conflicts on the old luvie-lv2 package, so upgrading
from v0.0.2 or earlier removes it rather than failing on the shared files. The
.rpm carries no equivalent -- luvie-lv2 was never published as one.

The .rpm is built on the same Ubuntu runner as the .deb, by CPack's RPM
generator (Debian's `rpm` package supplies rpmbuild). rpmbuild does not care
what distribution it runs on, and the dependencies it derives are soname-based,
so they resolve against the target system rather than the build host. Note it
puts the plugin in /usr/lib/lv2, not the %{_libdir}/lv2 that Fedora packages
use -- see the reasoning in cmake/Packaging.cmake.


Arch Linux (manual)
-------------------

Arch is served through the AUR, which is not part of the release workflow and
does not produce an artifact: an AUR package is a PKGBUILD that each user's
`makepkg` compiles from the release tag on their own machine. Nothing to build
in CI, nothing to attach to the release.

The recipe lives at packaging/aur/PKGBUILD; packaging/aur/README has the
publishing procedure. In short, after publishing the GitHub release:

    cp packaging/aur/PKGBUILD ../aur-luvie/     # edit pkgver, reset pkgrel to 1
    cd ../aur-luvie
    extra-x86_64-build                          # build in a clean chroot
    namcap luvie-*.pkg.tar.zst
    makepkg --printsrcinfo > .SRCINFO
    git commit -am "Update to 0.0.5" && git push

Keep packaging/aur/PKGBUILD in step with anything that changes what Luvie links
or where it installs -- that copy is the master, and the AUR repository holds a
copy of it.


Dry run
-------

Run the Release workflow manually from the Actions tab (workflow_dispatch). It
builds and packages everything and uploads the artifacts, but the release job is
gated on a tag push, so nothing is published. Use this to check a packaging
change without spending a tag.


Code signing (optional)
-----------------------

Unsigned builds work. macOS users get "unidentified developer" on first launch
and have to right-click -> Open once; Windows users get a SmartScreen warning.
Configuring the secrets below makes those go away; leaving them unset skips the
signing steps entirely, so a fork with no secrets still produces usable builds.

Repository secrets (Settings -> Secrets and variables -> Actions):

  MACOS_CERT_P12        Developer ID Application cert + key, .p12, base64'd:
                            base64 -i cert.p12 | pbcopy
  MACOS_CERT_PASSWORD   the .p12 export password
  MACOS_SIGN_IDENTITY   e.g. "Developer ID Application: Your Name (TEAMID)"

  APPLE_ID              Apple ID for notarization (optional; enables stapling,
  APPLE_TEAM_ID         which removes the first-launch prompt completely --
  APPLE_APP_PASSWORD    an app-specific password, not the account password)

  WINDOWS_CERT_P12      code-signing cert + key, .pfx/.p12, base64'd
  WINDOWS_CERT_PASSWORD its export password

Signing is only as good as the certificate: macOS notarization specifically
requires a "Developer ID Application" certificate from a paid Apple Developer
account. A self-signed certificate will sign but will not satisfy Gatekeeper.


If something fails
------------------

The tag stays put; fix the problem, delete the tag locally and remotely, and
re-push it:

    git tag -d v0.1.0
    git push --delete origin v0.1.0
    git tag -a v0.1.0 -m "Luvie 0.1.0"
    git push origin v0.1.0

Delete the draft release first if one was created, or the re-run will add a
second set of assets to it.

The dependency cache (keyed on CMakeLists.txt, which holds every pinned
revision) is the usual suspect for a build that fails only in CI. Clear it from
the Actions -> Caches page and re-run.
